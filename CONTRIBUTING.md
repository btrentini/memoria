# Contributing to Memoria

Start with the developer section of [README.md](README.md#how-to-develop--contribute). A full Xcode installation, Python and an Apple Silicon Mac are required for the native build. Rust is needed only for the optional worker.

## Work on a focused branch

```sh
git switch -c describe-your-change
make doctor
make app
make test
```

The checked-in Xcode project is generated by `Scripts/generate-project.py`. Change the generator when changing targets or build settings, then run `make project` and commit both files. Swift packages use local source modules. Preview fixtures belong in tests and benchmarks; production screens must use providers or explicit availability states.

Keep blocking collection off the main thread, histories and queues bounded, and missing/denied/stale measurements distinct from zero. Revalidate process identity before actions. Preserve the requirement for explicit force-kill confirmation and the separation between login startup and administrator operations. Do not add a permissive signing or authorisation fallback.

The Store targets have a separate public-API boundary. Run `make store-test` and `python3 Scripts/check-app-store.py --bundle build/store-preview/MemoriaStore.app` when changing shared code. Do not link process control, the helper or experimental private collectors into that edition.

## Verify what changed

Use unit tests for behaviour that can fail meaningfully, and disposable fixtures for process and socket checks. Report the command, configuration and outcome. A compile pass is not a runtime pass; an unavailable sensor is not a successful measurement. Update the requirements ledger and sanitised evidence when their scope changes.

Before a pull request:

```sh
git add <reviewed-files>
git diff --cached --check
python3 Scripts/check-publication.py
```

The publication check reads the staged blobs. Also use Gitleaks with the repository configuration when available. Never post secrets, private keys, authorisation blobs, real process IDs/captures, arguments, personal paths or machine identifiers. Synthetic identities in safety tests are appropriate. Build outputs and local diagnostic logs are ignored; a failed secret scan should be resolved before publication.

For dependency changes, inspect the pinned source and build scripts, record licences and modifications, update the SBOM and lockfiles, and run `python3 Scripts/verify-vendor.py` for the Rust vendor tree. The MIT application must not incorporate GPL implementation code from reference projects.

## Submit and review

Open a pull request describing the problem, the resulting behaviour and the checks actually run. Call out incomplete platform, signing, hardware or accessibility validation. Keep changes small enough to review; link related issues where useful. Do not infer a production-release pass from local test results.

Use [GitHub Issues](https://github.com/btrentini/memoria/issues) for sanitised bug reports and feature proposals. For suspected vulnerabilities, check [GitHub’s security reporting page](https://github.com/btrentini/memoria/security) for a private reporting option. If none is available, ask the maintainer for a private contact without disclosing the vulnerability. Do not put exploit details, credentials or private captures in a public issue.

## Releases

`make preview-package` produces an experimental installation archive only. Review its manifest, instructions, checksums and known issues before uploading it as a GitHub **pre-release**. Do not label an ad-hoc build as signed by Apple, notarised or production-ready. A stable user release requires the Developer ID, Gatekeeper, installation and acceptance checks in [Distribution.md](Documentation/Distribution.md). The App Store workflow has its own signing and submission gates.
